# Redis Cluster DEV on Proxmox (AlmaLinux 10 + Redis Open Source 8.10.2)

This project builds a 6-node Redis Cluster (3 masters and 3 replicas) with the same
topology as prod. A master and its own replica never run on the same Proxmox host.

## Layout

```
ansible.cfg
requirements.yml                   # ansible.posix (sysctl, firewalld)
inventory/hosts.yml                # groups: proxmox, pve_template, redis_cluster
inventory/group_vars/all/vars.yml  # every tunable value
inventory/group_vars/redis_cluster/vars.yml   # SSH user/become for the VMs
playbooks/tasks/preflight.yml      # VMID safety guard (shared by 01/02)
playbooks/templates/redis.conf.j2
playbooks/01_template.yml … 05_cluster.yml, 99_verify.yml
playbooks/98_connection_info.yml  # read-only: developer connection info from the live cluster
output/                            # generated by 98 (redis-dev-connection.md, redis-dev.env)
site.yml                           # imports 01-05
```

Deviations from the original spec, and why:

* `group_vars/` lives in `inventory/`, not at the project root. Ansible only picks up
  group_vars next to the inventory or next to the playbook being run. At the root it
  would load for `site.yml` but not for `playbooks/0X.yml` run on their own.
* `inventory/group_vars/all/vault.yml` (ansible-vault encrypted) holds only the
  SHA-512 crypt **hash** of the `almalinux` console password (`vault_almalinux_password_hash`).
  It is applied as cloud-init `--cipassword` (02) and enforced with the `user` module (03).
  SSH stays key-only. The vault password is read from `~/.ansible/redis-dev.vault-pass`
  (`ansible.cfg`). To change the password: `openssl passwd -6`, then
  `ansible-vault edit inventory/group_vars/all/vault.yml`, then run 03.
* Redis runs without a password; access is limited by firewalld
  to `10.50.200.0/24`. To turn auth on later: add `vault_redis_password` to vault.yml,
  set `redis_password: "{{ vault_redis_password }}"` in vars.yml, then run 04 (rolling
  restart). REDISCLI_AUTH and no_log are already wired up.
* Proxmox is driven with **SSH + `qm`/`pvesh`**, not `community.proxmox`. The disk
  import and `qm cloudinit dump` need a shell on the node anyway. Every mutating
  command is guarded by the current `qm config`. Cloning uses `qm clone --target <node>`
  (allowed because the disks are on shared Ceph). All other per-VM `qm` calls are
  delegated to the VM's own node, because `qm` only manages local VMs.

## Safety

* `pve_managed_vmids: [9010, 270-275]` is the complete list of VMs these playbooks may touch.
* `tasks/preflight.yml` runs first in 01 and 02. It reads `/cluster/resources` and
  **aborts** if any of those IDs belongs to a VM with a different name, on a different
  node, or without the `redis-dev` tag. When it aborts, nothing has been changed.
* 02 ARP-probes (`arping -D`) each VM IP from the target node before a VM is started;
  an IP that answers aborts the run. 03 refuses to touch a host whose hostname is not
  the VM name (protects against IP conflicts).
* Nothing in this project stops, migrates or deletes a VM. The one exception is the
  optional failover test in 99, which requires `-e run_failover_test=true` and re-checks
  the VM name first.

## Prerequisites (control node)

* The control node needs to reach 10.50.200.11-13 (root SSH to Proxmox) and

## Run: check first, then apply, one playbook at a time

```bash
ansible-playbook playbooks/01_template.yml --check --diff
ansible-playbook playbooks/01_template.yml
ansible-playbook playbooks/02_vms.yml --check --diff
ansible-playbook playbooks/02_vms.yml
ansible-playbook playbooks/03_os.yml --check --diff    # VMs must exist
ansible-playbook playbooks/03_os.yml                   # may reboot VMs once (THP)
ansible-playbook playbooks/04_redis.yml --check --diff
ansible-playbook playbooks/04_redis.yml
ansible-playbook playbooks/05_cluster.yml --check --diff
ansible-playbook playbooks/05_cluster.yml
ansible-playbook playbooks/99_verify.yml
ansible-playbook playbooks/99_verify.yml -e run_failover_test=true   # optional
```

Reading check-mode output: a `qm`/`redis-cli` step that **would run** shows as
`skipping … Command would have run if not in check mode` (add `-v` to see it). A step
that is already done shows as `skipping … Conditional result was False`. The read-only
steps (pvesh/qm config/cluster info) really do execute in check mode.

## Re-running

`ansible-playbook site.yml` is idempotent:

* 01 is skipped when 9010 is already our template.
* 02 never re-clones. It only re-applies `ipconfig0` if it drifted.
* 03 reboots only if the THP kernel argument had to be added.
* 04 restarts Redis only when `redis.conf` changes, one node at a time (`serial: 1`).
* 05 checks every shard (master+replica pair). A pair counts as healthy in **either
  direction**, so a failed-over shard is left as it is. Cluster creation runs only
  when all 3 masters are fresh. Any unexpected state stops the run without making changes.

## App connection (cluster mode)

To produce the developer handoff from the **live** cluster (current roles, version,
auth/TLS status, allowed subnets), run this read-only playbook:

```bash
ansible-playbook playbooks/98_connection_info.yml
```

It prints a summary and writes `output/redis-dev-connection.md` (the full handoff with
client snippets for Spring Boot, Lettuce, Jedis, Python, ioredis, node-redis, Go, .NET, PHP)
and `output/redis-dev.env`. It never prints a password, only whether auth is enabled.

## Destroy the DEV environment (run manually on any Proxmox node)

1. Confirm the IDs are still ours. Every line must say `OK`:

```bash
pvesh get /cluster/resources --type vm --output-format json | python3 -c '
import sys, json
want = {9010:"alma10-redis-dev-tpl",270:"redis-dev-01",271:"redis-dev-02",272:"redis-dev-03",273:"redis-dev-04",274:"redis-dev-05",275:"redis-dev-06"}
for v in sorted(json.load(sys.stdin), key=lambda v: v["vmid"]):
    if v["vmid"] in want:
        ok = v["name"] == want[v["vmid"]] and "redis-dev" in v.get("tags", "").split(";")
        print(v["vmid"], v["node"], v["name"], "OK" if ok else "MISMATCH - DO NOT DELETE")'
```

2. Stop and delete the VMs. `pvesh` works for any node from any node:

```bash
for p in DC-A-PVE-11:270 DC-A-PVE-12:271 DC-A-PVE-13:272 DC-A-PVE-11:273 DC-A-PVE-12:274 DC-A-PVE-13:275; do
  n=${p%%:*}; id=${p##*:}
  pvesh create /nodes/$n/qemu/$id/status/stop
  pvesh delete /nodes/$n/qemu/$id --purge 1 --destroy-unreferenced-disks 1
done
```

3. Optionally, delete the template and the cached image:

```bash
pvesh delete /nodes/DC-A-PVE-11/qemu/9010 --purge 1 --destroy-unreferenced-disks 1
```

```bash
rm -rf /var/tmp/redis-dev-image
```

Rebuild afterwards with `site.yml`. VM SSH host keys are not stored in known_hosts
(`inventory/group_vars/redis_cluster/vars.yml`), so rebuilds don't trigger key warnings.
